# P10 — Agent 4: i18n Audit (stray Arabic in EN / stray English in AR)

**Branch:** `feature/p10-i18n` → merged into `integration/phase10`
**Scope (owned files only):** i18n dictionaries (`src/config/strings.ts`, `src/i18n/dict/*`) + components that
hardcoded user-facing strings (replaced with i18n keys). **Not touched:** calculations, auth/session logic,
custom-plan generation, todo/commitment functionality — only strings/keys.

## Problem (from real testers)
Switching to **English** left several UI strings in **Arabic**, and switching to **Arabic** left several in
**English**. The app has a two-layer i18n system (`config/strings.ts` shell dictionary + per-screen dicts under
`src/i18n/dict/`), but many user-facing strings bypassed it — hardcoded in components, or pulled from
single-language config/data files.

## Audit method
- Scanned every live `*.tsx` for non-comment Arabic string literals (custom Node scanner) → 292 candidate lines
  in 63 files, then triaged (excluded JSX comments, data names, dead landing sections).
- Confirmed the 13 legacy marketing sections (`Hero`, `Pricing`, `Faq`, `Solution`, …) are **dead code**
  (0 imports) and out of scope.
- Verified with a headless-browser pass (`scripts/run-p10-i18n-proof.mjs`, Chromium via CDP): loaded the built
  production app, seeded a completed guest onboarding, toggled EN/AR via `localStorage`, screenshotted every
  screen, and scanned rendered `innerText` for stray-language strings.

truth; English is layered on for display only.

## Intentional exceptions (not bugs)
1. **Language toggle** shows the *other* language's own name (`العربية` / `English`) and `ع`/`EN` — by design.
2. **Brand logo** renders `قِمّة` in Arabic / `Qimmah` in English (from the shell dict) — correct per mode.
3. **Item names stay bilingual by design** (documented Arabic-primary): exercise, food, meal, supplement,
   medication, and **commitment** names. In AR mode some show an English reference (e.g. `تمرين اليوم — Today
   workout`, split `علوي/سفلي (Upper/Lower)`). This is the pre-existing bilingual-reference convention and lives
   in `data/` + the commitment/todo display helpers — **left untouched per the "do not change todo
   functionality / data names" ownership rule.**
4. **Acronyms** (`BMR`, `TDEE`, `BMI`, `RPE`) are unit/technical tokens shown identically in both languages.
5. **Muscle group names** in the weekly map selection stay Arabic (data taxonomy, `SLUG_LABEL_AR`); the
   surrounding UI hint now translates.
6. **Food category taxonomy** (`FoodCategory`, incl. `منتج ممسوح بالباركود`) is a typed Arabic data enum — left
   as data (consistent with all other food categories).

## Risks / notes
- `authContext`, `SplashScreen`, `Skeleton`, and the achievements `engine` read the persisted language via
  `getLanguage()` (not the React context) because they render outside or before the provider / in class or
  non-component code. Language changes take effect on the next render of these surfaces, which is fine for
  toasts, splash, and error fallbacks.
- The onboarding wizard's raw `<select>` option lists (StepBody, etc.) still use `calculators.ts` Arabic labels
  in the dropdowns; the bilingual helper (`lib/i18nLabels.ts`) is in place to migrate them, but they were left
  as-is to avoid touching onboarding form behavior in this pass. Visible **display** of those values (chips,
  profile cards, calorie explainer) is translated.
- No calculation, auth flow, plan-generation, or commitment logic was modified — only strings/keys and the
  language-selection of display text.
