# P8 Agent 1 — قاعدة بيانات المنتجات الداخلية (الأساس)

## الهدف
طبقة بيانات خالصة (بلا واجهة مستخدم) لمنتجات مُعرَّفة بالباركود، تُغذّيها عدة مصادر
(Open Food Facts، مصدر مرخّص، مستخدم، OCR) دون تكرار الباركود أبدًا، مع سجل تدقيق كامل
لكل عملية إضافة/دمج/تعديل/تغيير حالة. هذه الوحدة أساس يستورد منه بقية وكلاء P8
(الكاميرا/OCR/الإضافة اليدوية) — لا تعتمد هي على أي منهم.

## الملفات (كلها جديدة تحت `src/features/products/`)
- `types.ts` — الأنواع: `StoredProduct`, `ProductSource`, `AuditEntry`, `ProductInput`, `MacroSet`, إلخ.
- `store.ts` — المخزن المحلي (`localStorage`): `getProduct`, `upsertProduct` (منطق الدمج)،
  `editProduct`, `setProductStatus`, `listByStatus`, `searchProducts`, `getAuditLog`.
- `resolve.ts` — `resolveBarcode()` بترتيب المصادر + آلية تسجيل الجالبات البعيدة
  (`registerOpenFoodFactsFetcher`, `registerAuthorizedSourceFetcher`).
- `index.ts` — الواجهة العامة الوحيدة الموصى بالاستيراد منها لبقية الوكلاء.

لم أُلمس أي ملف خارج `src/features/products/` (لا phrases، لا exercises، لا خريطة العضلات،
ولا واجهة الباركود الحالية في `src/features/barcode/`).

## التخزين
- `qimmah:products:v1` — خريطة `barcode → StoredProduct`.
- `qimmah:products:audit:v1` — مصفوفة `AuditEntry[]` مرتّبة زمنيًا.
- نفس نمط الحماية المستخدم في بقية المشروع: فحص `typeof window` + `try/catch` صامت
  (تخزين ممتلئ أو معطّل لا يُسقط التطبيق).

## منطق الدمج (Dedup)
`upsertProduct(input)` لا يُنشئ باركودًا مكررًا أبدًا:
1. **منتج جديد** → يُنشأ بمصدر واحد (`sources: [input.source]`)، الحالة الافتراضية `imported`
   (أو الحالة الصريحة إن مُرِّرت). سجل تدقيق `add`.
2. **منتج موجود** →
   - **المصادر**: المصدر الجديد يُضاف إلى `sources[]`؛ إن كان نفس `sourceName` موجودًا مسبقًا
     يُحدَّث مكانه (لا يتكرر نفس المصدر مرتين — كل استيراد لاحق من نفس OFF مثلًا يحدّث
     `importedAt`/`sourceUrl` فقط).
   - **القيم الغذائية**: تُقاس "الاكتمال" بعدد الحقول غير الصفرية (kcal/protein/carbs/fat).
     تُفضَّل القيم الأكثر اكتمالًا؛ عند التساوي تُفضَّل القيم الجديدة (الأحدث).
   - **التعارض**: يُقارَن فقط إن كان الأساس (`per`) متطابقًا بين المصدرين. إن اختلفت قيمتان
     حقيقيتان (كلتاهما > 0) بأكثر من 10% تفاوتًا → الحالة تتحوّل تلقائيًا لـ `pending_review`
     (ما لم يُمرَّر `status` صريح من المستدعي). سجل تدقيق `merge`، وإن تغيّرت الحالة فعليًا
     يُضاف أيضًا سجل `status_change` منفصل يوثّق السبب.
3. **تعديل يدوي مباشر**: `editProduct()` لتصحيحات المراجعة، و`setProductStatus()` لتغيير
   الحالة صراحةً (مثل توثيق منتج كـ `verified` بعد مراجعة بشرية) — كلاهما يسجّل تدقيقًا
   (`edit` / `status_change`) بدل المرور بمنطق دمج المصادر.

اختُبِر هذا المنطق يدويًا بسكربت مؤقت (بُنِي بـ esbuild وشُغِّل بـ Node مع شِم بسيط
لـ `localStorage`، ثم حُذف قبل الالتزام): إضافة أولى، دمج بفارق ضمن التفاوت المقبول
(يبقى `imported`)، دمج بفارق سعرات كبير (900 مقابل ~400 → `pending_review`)، إعادة
استيراد نفس المصدر (لا يتكرر)، `getProduct`/`listByStatus`/`searchProducts`، وسجل
التدقيق الكامل — كل الحالات نجحت (`ALL PASS`).

## البحث (`searchProducts`)
مطابقة نصية غير حسّاسة لحالة الأحرف على `name`/`brand` (substring)، مع ترتيب النتائج التي
تبدأ فعليًا بنص البحث أولًا.

## ترتيب المصادر (`resolveBarcode`)
```
resolveBarcode(barcode) →
  1) الداخلي (getProduct)                         — إن وُجد، يُرجَع فورًا.
  2) Open Food Facts (جالب مُسجَّل عبر registerOpenFoodFactsFetcher)
  3) مصدر مرخّص (جالب مُسجَّل عبر registerAuthorizedSourceFetcher)
  4) null (foundIn: 'not_found')                   — الواجهة توجّه لمسار OCR/إضافة يدوية.
```
أي نتيجة من مصدر بعيد (2 أو 3) تُخزَّن فورًا داخليًا عبر `upsertProduct` بحالة `imported`
فلا يتكرر نفس الطلب البعيد لاحقًا لنفس الباركود.

**لماذا "خطاف تسجيل" لا استيراد مباشر**: هذه الوحدة لا تستورد من
`src/features/barcode/openFoodFacts.ts` مباشرة رغم وجود تطبيق حقيقي هناك بالفعل
(`lookupBarcode`) — بل تُعرِّف توقيع `RemoteFetcher` ودالة `registerOpenFoodFactsFetcher`
مع جالب افتراضي لا يفعل شيئًا (`async () => null`) حتى تُصرَّف الوحدة بمفردها بلا اعتماديات
خارج مجلدها، تمامًا كما هو مطلوب. الوكيل الذي يربط الواجهة (Agent 2/4) يستدعي مثلًا:
```ts
import { registerOpenFoodFactsFetcher } from '@/features/products'
import { lookupBarcode } from '@/features/barcode/openFoodFacts'

registerOpenFoodFactsFetcher(async (barcode) => {
  const off = await lookupBarcode(barcode)
  if (!off) return null
  return {
    name: off.name,
    brand: off.brands,
    per: '100g',
    servingSize: off.servingSize,
    kcal: off.caloriesPer100g,
    protein: off.proteinPer100g,
    carbs: off.carbsPer100g,
    fat: off.fatPer100g,
  }
})
```
عند بدء تشغيل التطبيق (مرة واحدة)، دون أي تعديل على ملفات `src/features/barcode/`.

## سجل التدقيق (`AuditEntry`)
كل عملية كتابة (`add`/`edit`/`merge`/`status_change`) تُسجَّل بـ: الباركود، الفعل،
`by` (منفّذ العملية — افتراضيًا اسم المصدر)، الوقت، اسم المصدر، وملاحظة اختيارية. يُقرأ
عبر `getAuditLog(barcode?)` — بلا وسيط يُرجع السجل كاملًا.

## مخاطر ومتابعات
- **لا إطار اختبارات آليًا في المشروع** (لا Vitest/Jest) — التحقق الحالي يدوي فقط عبر
  سكربت مؤقت. يُنصح لاحقًا بإضافة Vitest إن تعدّدت طبقات المنطق غير المرئية للـ UI.
- **تفاوت التعارض 10%** قيمة معقولة لكن اجتهادية — قابلة للتعديل بسهولة
  (`CONFLICT_TOLERANCE_RATIO` في `store.ts`) إن ظهرت حالات حقيقية تتطلب عتبة مختلفة.
- **لا حد أقصى لحجم `localStorage`** — مع نمو قاعدة المنتجات (آلاف الباركودات) قد
  تحتاج لاحقًا لترحيل لـ IndexedDB؛ خارج نطاق هذه المرحلة (v1.0 frontend-only).
- **الربط الفعلي بـ Open Food Facts** غير مُنفَّذ هنا عمدًا (خطاف تسجيل فقط) — يحتاج
  سطرًا واحدًا من وكيل الواجهة عند الإقلاع (مثال أعلاه) لتفعيله فعليًا.
