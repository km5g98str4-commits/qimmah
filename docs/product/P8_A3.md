# P8 Agent 3 — إضافة منتج يدويًا + قراءة الجدول الغذائي بـ OCR

## الهدف
عند فشل مسح الباركود في إيجاد منتج، لا يوصد الطريق: يقدر المستخدم يضيف المنتج يدويًا
(بالباركود معبّأً مسبقًا)، اختياريًا يصوّر جدول الحقائق الغذائية وتُقرأ تلقائيًا (OCR) لتعبئة
القيم، ودائمًا تُحفظ الصور المرفقة — لا يُفقَد أي إدخال حتى لو فشلت القراءة التلقائية بالكامل
أو تُرك المستخدم الحقول فارغة.

## قاعدة المنتجات (وكيل P8-A1) — استُهلكت مباشرة
عند بدء التنفيذ لم تكن قاعدة منتجات وكيل P8-A1 (`upsert` + `StoredProduct`) موجودة بعد في
`integration/phase8`، فبُنيت نسخة محلية مؤقتة داخل `addProduct/**` بعقد متوافق كي لا يتعطّل
العمل. بعد أن ظهرت وحدة P8-A1 الفعلية (`src/features/products/{types,store,resolve,index}.ts`،
مدموجة في `integration/phase8` بواسطة الوكيل 1 والوكيل 2) عبر `git merge` لأحدث
`integration/phase8` داخل هذا الفرع، حُذفت النسخة المحلية المؤقتة (`productStore.ts`/`types.ts`)
والآن `AddProductScreen.tsx` يستهلك **مباشرة** `upsertProduct`, `getProduct`, `searchProducts`,
`getAuditLog`, و`StoredProduct`/`ProductPer` من `@/features/products` — لا نسخة مكرّرة، لا محاذاة
لاحقة مطلوبة. الملفات المتبقية داخل `addProduct/**` (الشاشة، الصور، OCR، النصوص) لم تتغيّر
جوهريًا، فقط استيراداتها.

فروق بسيطة تكيّفت معها الشاشة مع الشكل الفعلي لقاعدة P8-A1 (مختلف عن افتراضي الأولي):
- **الباركود هو المفتاح الأساسي** (`StoredProduct.barcode: string`، غير اختياري) — إضافة
  يدوية بحتة بلا باركود (لم تأتِ من مسح فاشل) تولّد مفتاحًا محليًا فريدًا
  (`local:{timestamp}{random}`) حتى تتوافق مع القاعدة، بدل تعطيل الحفظ.
- **المصدر مصفوفة `sources[]`** لا حقل مفرد — الحفظ يمرّر
  `source: { sourceName: 'user', importedAt: <ISO> }`، وقاعدة P8-A1 تدمجه (تحديث لا تكرار عند
  نفس `sourceName`) بدل إضافة سطر متكرر.
- **`status` تمرير صريح** (`user_submitted`/`pending_review`) يتجاوز منطق كشف التعارض التلقائي
  في القاعدة (المخصَّص لدمج مصادر متعددة مثل OFF/مرخّص) — يطابق طلب المهمة الأصلي بالضبط.
- أضفتُ `note` اختياريًا عند الحفظ يوثّق أن OCR ساعد في التعبئة — يظهر في سجل التدقيق
  المشترك (`getAuditLog`) بلا أي تعديل على القاعدة نفسها.

## الملفات (كلها جديدة داخل `src/features/products/addProduct/**`)
- `ocr.ts` — `extractNutritionFromImage` (تحميل ديناميكي لـ `tesseract.js` عند أول استدعاء
  فقط) + `parseNutritionText` (أنماط نصّية عربي/إنجليزي best-effort، دالة نقية قابلة للاختبار
  بمعزل عن الشبكة/العامل Worker).
- `strings.ts` — نصوص عربي/إنجليزي محلية لهذا المجلد (لم أُعدِّل `i18n/dict/nutritionScreen.ts`
  المشترك حتى لا أتقاطع مع أقسام أخرى).
- `PhotoCapture.tsx` — التقاط صورة عبر كاميرا حيّة (`getUserMedia` + `canvas`) مع تراجع فوري
  لاختيار صورة من الاستديو (`<input type=file>`) عند رفض الصلاحية أو عدم الدعم. مستقل تمامًا
  عن كاميرا الماسح (`src/features/barcode/BarcodeCamera.tsx` — وكيل 4) — لا كود مشترك.
- `AddProductScreen.tsx` — الشاشة الكاملة: الحقول، الصور، قسم OCR، الحفظ عبر `@/features/products`.
- `index.ts` — نقطة استيراد مقترحة للاستهلاك الخارجي (تعليق فيه مثال `React.lazy`).
- `scripts/p8-a3-proof.ts` + `scripts/run-p8a3-proof.mjs` + npm script `proof:p8a3` — إثبات
  headless (نفس نمط `run-p5-reset-proof.mjs`: esbuild + `localStorage` مُحاكى) يستهلك قاعدة
  P8-A1 الفعلية.

## تدفّق الإضافة
1. الحقول: الاسم، العلامة التجارية (اختياري)، القيم لكل حصّة/100غ، حجم الحصّة (اختياري)،
   سعرات/بروتين/كارب/دهون (حدود من `@/lib/validation` — `NUM_LIMITS.quickCalories/quickProtein/
   quickMacro` نفس الحدود المستخدمة في الإضافة السريعة الحالية، إعادة استخدام لا تكرار).
2. الباركود مُعبَّأ مسبقًا (prop) ويُعرض للقراءة — الشاشة تعمل أيضًا بلا باركود (تولَّد مفتاح
   محلي تلقائيًا عند الحفظ، انظر أعلاه).
3. صورتان اختياريتان: صورة المنتج + صورة جدول الحقائق الغذائية، كل واحدة عبر `PhotoCapture`.
4. إن وُجدت صورة الجدول الغذائي، يظهر قسم OCR بزر «استخرج القيم تلقائيًا» + تنويه صادق أن
   القراءة مساعِدة وقد تُخطئ.
5. عند نجاح الاستخراج الجزئي/الكامل: تُعبَّأ الحقول المكتشفة فقط، ويظهر **checkbox إلزامي**
   («راجعت القيم المستخرجة وصحّحت أي خطأ فيها») يمنع زر الحفظ حتى يُؤشَّر — يحقّق شرط «تأكيد/
   تصحيح قبل الحفظ». إن لم يُستخدم OCR إطلاقًا، لا يظهر هذا القيد.
6. عند فشل OCR كليًا (شبكة/عامل/لا أرقام واضحة): رسالة صادقة + الحفظ يبقى متاحًا فورًا (لا قيد
   تأكيد لأنه لا توجد قيم مُستخرَجة لتأكيدها).
7. الحفظ: `upsertProduct({ ..., source: { sourceName: 'user', ... }, status })` عبر
   `@/features/products`. `status` = `user_submitted` إن وُجدت قيمة غذائية واحدة > 0 على
   الأقل، وإلا `pending_review` (للمراجعة لاحقًا). اسم المنتج إن تُرك فارغًا يُستبدَل تلقائيًا
   بنص صادق («منتج جديد · {باركود}») بدل حجب الحفظ — **لا يُفقَد أي إدخال أبدًا**.

## مكتبة OCR + التحميل الكسول + صدق الدقة
- **المكتبة**: `tesseract.js@^7.0.0`. المهمة وصفتها بـ MIT؛ رخصة الحزمة المنشورة فعليًا حسب
  `npm view` هي **Apache-2.0** (ترخيص متساهل أيضًا يسمح بالاستخدام التجاري بلا قيود جوهرية) —
  فرق توثيقي بسيط بين الطلب والواقع، مُسجَّل هنا بصراحة وليس عائقًا.
- **تحميل كسول**: `ocr.ts` لا يستورد `tesseract.js` سكونيًا؛ الاستيراد فقط داخل
  `extractNutritionFromImage` عبر `await import('tesseract.js')` — نفس أسلوب تحميل
  `@zxing/browser` (يُحمَّل فقط عند فتح لوحة المسح). تحقّقتُ عبر `esbuild --bundle --splitting`
  أن نقطة استهلاك `ocr.ts` وحدها (بدون استدعاء الدالة) تُنتج chunk دخول ~1.5kB بينما كود
  tesseract.js ينعزل في chunk منفصل — لا يُحمَّل إلا عند نقرة «استخرج القيم تلقائيًا» فعليًا.
  `npm run build` الكامل للتطبيق يبقى بلا أي إضافة لحزمة الدخول لأن `AddProductScreen` غير
  مُستورَدة بعد من أي مسار تشغيل (بانتظار الدمج، انظر أدناه).
- **صدق الدقة**: نص الواجهة (`ocr.ts`/`strings.ts`) يقول صراحة إن القراءة «مساعِدة فقط وقد
  تُخطئ» وتُلزم الشاشة بمراجعة/تصحيح قبل الحفظ (checkbox في الفقرة 5 أعلاه) — لا وعد بدقّة.
  الاستخراج نفسه best-effort بحت: أنماط نصّية بسيطة (عربي/إنجليزي)، تُعيد `undefined` لأي قيمة
  غير واضحة بدل تخمين رقم خاطئ (مُثبَت في proof).

## التقاط الصور — لا يُفقَد أي إدخال
- كل من صورة المنتج وصورة الجدول الغذائي تُحفظان كـ data URL على `StoredProduct.imageUrl` /
  `nutritionImageUrl` بغض النظر عن نجاح OCR من عدمه.
- رفض صلاحية الكاميرا يُعامَل بلطف: `PhotoCapture` يتراجع فورًا لخيار «اختر من الاستديو»
  (`<input type=file>` عادي بلا `capture` — يعمل حتى بلا أي صلاحية كاميرا) مع رسالة صادقة، ولا
  يوقف تدفّق الإضافة أبدًا.
- زر الحفظ **غير مقيَّد** بوجود صور أو قيم غذائية — القيد الوحيد هو تأكيد OCR (فقرة 5 أعلاه)،
  وهو قيد متعمَّد بنقرة واحدة وليس خطر فقدان بيانات.

## الإثبات
`npm run proof:p8a3` (esbuild + `localStorage` مُحاكى، بلا شبكة، يستهلك `@/features/products`
الفعلية) — 20 فحصًا، كلها ناجحة:
- إضافة منتج بباركود لم يُوجد عبر Open Food Facts → `upsertProduct` بقيم كاملة، مصدر `user`
  مسجَّل في `sources[]`، `status: 'user_submitted'`، الصورتان محفوظتان.
- «مسح تالٍ» لنفس الباركود (`getProduct`) يحلّ المنتج محليًا فورًا — بلا أي طلب شبكة.
- `upsert` لنفس الباركود مرة أخرى يدمج في نفس السجل (لا تكرار في `sources[]` ولا في
  `searchProducts`)، وسجل التدقيق (`getAuditLog`) يوثّق `add` ثم `merge`.
- منتج بلا أي قيمة غذائية (محاكاة فشل OCR الكامل) يُحفظ ويُعلَّم `pending_review`، وصورة
  الجدول الغذائي تبقى محفوظة — **لا فقدان للإدخال**.
- منتج بلا باركود (إضافة يدوية بحتة) يُحفظ بمفتاح محلي مولَّد ويُحلّ لاحقًا بنجاح.
- `parseNutritionText` يستخرج السعرات/البروتين/الكارب/الدهون بنجاح من نص عربي وإنجليزي
  نموذجي، ويعيد `undefined` لنص بلا أرقام واضحة (لا تخمين).

**اختبار مباشر إضافي في متصفح حقيقي (Playwright، ليس جزءًا من الالتزام):** شغَّلت الشاشة عبر
مُعاينة مؤقتة (أُزيلت قبل الالتزام) على 390×844، **قبل** دمج قاعدة P8-A1 الفعلية (كانت الشاشة
حينها تستهلك النسخة المحلية المؤقتة — نفس واجهة `upsert`/`StoredProduct` فمنطق الواجهة والحفظ
لم يتغيّر بعد التبديل):
- RTL صحيح (زر الإغلاق يسارًا، العنوان يمينًا، الحقول والاتجاه سليمان).
- رفض الكاميرا (بيئة الحاويات بلا كاميرا حقيقية) → رسالة صادقة + زر «اختر من الاستديو» يعمل.
- رفع صورة جدول غذائي حقيقية (نص Calories/Protein/Carbohydrate/Fat) عبر «اختر من الاستديو»
  ونقر «استخرج القيم تلقائيًا»: بيئة الحَجْر (sandbox) هنا تمنع الوصول لشبكة `cdn.jsdelivr.net`
  (403 عبر البروكسي) التي يجلب منها `tesseract.js` عامل الـ Worker افتراضيًا — هذا أثبت عمليًا
  **مسار الفشل الكامل الحقيقي**: رسالة صادقة ظهرت («ما قدرنا نقرأ الجدول تلقائيًا…»)، زر
  الحفظ بقي متاحًا فورًا، والحفظ نجح فعليًا مع حفظ صورة الجدول الغذائي و`status: pending_review`
  واسم افتراضي صادق — تمامًا كما تنبّأ التصميم. منطق الحفظ نفسه (غير متأثر بمصدر التخزين)
  تحقّق مجددًا عبر `proof:p8a3` بعد التبديل لقاعدة P8-A1 الحقيقية.

`src/features/products/addProduct/**`، وتلك الملفات مسار مسح الباركود لا أملكه. الربط المقترح
لاحقًا (تعديل بسيط في `QuickMealLogger.tsx` حيث `onManualFallback` يستدعى اليوم فقط لفتح تبويب

  import('@/features/products/addProduct').then((m) => ({ default: m.AddProductScreen })),

// ... onManualFallback={(barcode) => { setScanOpen(false); setAddProductBarcode(barcode) }}
// ... {addProductBarcode !== null && (
//   <Suspense fallback={null}>
//     <AddProductScreen lang={lang} barcode={addProductBarcode} onSaved={...} onClose={...} />

تعديلان صغيران خارج نطاق ملفاتي.

## المخاطر ومتابعات
1. **الربط بواجهة المسح لم يُنفَّذ** (تعمّدًا، تفادي تعارض ملفات) — انظر «الدمج» أعلاه. هذا
   الأثر الوحيد المتبقي على «قابلية الاستخدام الفعلية» للميزة؛ المنطق والتخزين جاهزان بالكامل.
2. **`tesseract.js` يعتمد افتراضيًا على CDN (`jsdelivr`)** لجلب عامل الـ Worker + نواة wasm +
   بيانات اللغة وقت التشغيل. هذا طبيعي وسيعمل في متصفح مستخدم حقيقي بشبكة عادية، لكن على
   شبكات مقيَّدة (مثل بيئة الاختبار هذه) يفشل الجلب بالكامل — وهو بالضبط المسار الذي أثبتّه حيًّا
   ولم يعطّل الحفظ. تحسين مستقبلي: استضافة أصول tesseract.js محليًا (`corePath`/`workerPath`/
   `langPath` في `createWorker`) بنفس أسلوب vendoring صور WorkoutX في P5، لضمان عمل OCR دون
   اعتماد على CDN خارجي.
3. **ترخيص tesseract.js**: Apache-2.0 فعليًا (وليس MIT كما ورد في وصف المهمة) — لا يزال
   متساهلًا وتجاريًا، لكن يستحق تصحيح التوثيق الداخلي.
4. **حجم حزمة OCR** غير مقاس داخل `npm run build` الحالي لأن الميزة غير مربوطة بعد بأي مسار
   تشغيل فعلي؛ القياس عبر `esbuild --splitting` يدويًا (موثّق أعلاه) يثبت الانعزال لكنه ليس
   رقمًا من مخرجات Vite نفسها. يجب التحقّق مجددًا من حجم `dist/assets/*ocr*` بعد الدمج الفعلي
   بواجهة التشغيل.
5. **مفاتيح محلية بلا باركود (`local:...`)** لن تتوحّد أبدًا مع منتج حقيقي إن ظهر لاحقًا
   بباركود فعلي لنفس الصنف — قرار منتج معقول (لا نملك باركودًا حقيقيًا لنربط به) لكن يستحق
   ملاحظة عند بناء واجهة مراجعة `pending_review`/`listByStatus` لاحقًا.
