# P10 · Agent 3 — بقاء الجلسة (Session Persistence)

**الحالة:** ✅ مُصلَح ومُثبَت (Gates خضراء).
**النطاق:** طبقة المصادقة/الجلسة + بوابة التوجيه في `App.tsx` فقط.

---

## المشكلة (كما رصدها المختبِر)

مستخدم سجّل دخوله، يغلق التطبيق/المتصفّح، وعند العودة **يُطالَب بتسجيل الدخول من جديد** —
رغم أنّ الجلسة يُفترض أن تبقى على الجهاز حتى تسجيل خروج صريح.

## التشخيص

راجعنا النقاط الثلاث المطلوبة:

1. **ضبط عميل Supabase — سليم.**
   في `src/lib/supabaseClient.ts` الإعداد صحيح أصلًا:
   `persistSession: true` · `autoRefreshToken: true` · `detectSessionInUrl: true` ·
   `storageKey: 'qimmah:supabase-auth:v1'` (التخزين الافتراضي `localStorage`).
   الجلسة **تُحفَظ فعلًا** وتُستعاد: `supabase.auth.getSession()` يعيد الجلسة بمعرّف
   المستخدم الصحيح بعد إعادة التحميل (تحقّقنا منه بالتسجيل داخل المتصفّح).

2. **تدفّق الإقلاع — هنا الخلل الجذري.**
   `authContext` ينتظر `getSession()` ويضبط `loading`، لكنّ `App.tsx` كان:
   - يحسب مسار الإقلاع `initialRoute()` **بمعرّف المستخدم = null** (لأنّ الجلسة ما زالت
     تُستعاد بشكل غير متزامن) → يُنزّل المستخدم المسجَّل إلى شاشة البداية `start`
     (التي تعرض زرّ «تسجيل الدخول»).
   - أسوأ: تأثير مزامنة `view → hash` كان يكتب المسار المؤقّت (`#/start`) في رابط
     الصفحة **قبل** جهوزية المصادقة، فيطمس الرابط الأصلي (مثل `#/dashboard`).
   - عند اكتمال الاستعادة، تأثير المصالحة كان يستدعي `guardRoute(currentView, uid)`
     فقط، و`guardRoute` **لا يرفع** مسارًا غير رئيسي؛ فيبقى العرض عالقًا على `start`
     رغم وجود جلسة صالحة → «سجّل الدخول من جديد».
   - كما كان يُعرَض `start` أثناء نافذة الاستعادة بدل حالة تحميل.

3. **مسح تخزين المصادقة عند الإقلاع — لا يوجد.**
   `resetQimmah()` (الوحيد الذي يحذف `qimmah:supabase-auth:v1`) لا يُستدعى إلا يدويًا من
   الإعدادات/مراجعة الإعداد. لا service-worker يمسح التخزين. فالسبب توجيهي بحت لا تخزيني.

**الجذر:** سباق إقلاع في التوجيه — القرار يُتّخذ قبل استعادة الجلسة، ثم لا يُصحَّح.

## الإصلاح (في `src/App.tsx` فقط)

1. **بوابة تحميل:** أثناء `auth.loading` نعرض `<AppLoading />` (مؤشّر قصير) بدل أي شاشة —
   فلا تظهر شاشة الدخول لمستخدم لديه جلسة صالحة.
2. **حسم المسار بعد جهوزية المصادقة:** أول مرّة تُستعاد فيها الجلسة نحسب
   `initialRoute(uid)` **بالمعرّف الحقيقي ومع احترام الـ hash** فيهبط المستخدم حيث كان
   (لوحة/تغذية/…)، لا على `start`. (عبر مرجع `didInitialAuthRoute`.)
3. **حماية الرابط الأصلي:** لا نكتب `view → hash` قبل حسم مسار الإقلاع الأول، حتى لا
   يُطمَس الرابط الأصلي بالمسار المؤقّت أثناء التحميل. نكتب الـ hash صراحةً عند الحسم
   الأوّل للحفاظ على سلوك الضيف/الروابط العميقة **كما كان تمامًا**.

> عميل Supabase و`authContext` لم يتغيّرا (الإعداد كان سليمًا). الإصلاح كلّه في بوابة
> التوجيه.

## الإثبات (متصفّح Headless)

`scripts/run-p10a3-session-proof.mjs` (Playwright) يزرع جلسة Supabase محفوظة (كما يخزّنها
`supabase-js` تحت `storageKey`) ويشغّل التدفّق على بناء الإنتاج:

| الخطوة | النتيجة |
|---|---|
| فتح التطبيق بجلسة محفوظة | `#/dashboard` · لا شاشة دخول · داخل التطبيق ✓ |
| إعادة تحميل قاسية (hard reload) | ما زال داخل التطبيق · لا مطالبة بالدخول ✓ |
| إعادة تشغيل كاملة (سياق متصفّح جديد بنفس التخزين) | ما زال مسجّلًا · هبط حيث كان `#/dashboard` ✓ |
| تسجيل خروج صريح (مسح مفتاح الجلسة) | عاد إلى `#/start` (زر «تسجيل الدخول» ظاهر) ✓ |

**النتيجة:** `✅ ALL PASS`.

للتشغيل:

```bash
npm run build && node scripts/run-p10a3-session-proof.mjs
```

## المخاطر / ملاحظات

- **حالة التحميل:** إن تعذّر حسم `getSession()` (نادر — قراءة محلية) يبقى المؤشّر ظاهرًا؛
  لا استدعاء شبكة في مسار الاستعادة (تجديد التوكن منفصل عبر `autoRefreshToken`).
- **وضع الضيف + تسجيل الخروج:** بلا تغيير سلوكي؛ الرابط الأصلي والروابط العميقة محفوظة.
- **iOS Safari / PWA:** يعتمد بقاء `localStorage`؛ لا يوجد service-worker يمسح مفتاح
  المصادقة، ولا اعتماد على تخزين جلسي (session storage).
- **بيئة الإثبات:** سكربت Playwright يثبّت مسار Chromium المُثبَّت مسبقًا في هذه البيئة؛
  في بيئة أخرى بدّل `executablePath` حسب متصفّح Playwright المتاح.
