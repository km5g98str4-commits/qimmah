# Salla → Premium — عقد التكامل

**الموجة:** `[CTO-BACKEND-001]` · **الفرع:** `claude/salla-activation` · **الأساس:** `df85c77`
**النطاق:** خادم فقط. لا واجهة ولا بوّابة مسارات ولا شاشة Premium — تلك موجات لاحقة.

> **هذا الملف عقدٌ لا شرح.** ما يبنيه العميل (iOS/Web) لاحقًا يستهلك ما هنا حرفيًا.
> عند أي تعارض بينه وبين الهجرات، **الهجرات تفوز** (نفس قاعدة وثيقة المعمارية).

## 1. الدورة كاملة

```
شراء في سلة
   └─► webhook موقَّع  ──►  supabase/functions/salla-webhook
                              ① تحقّق HMAC        (قبل أي كتابة)
                              ② تحليل الحمولة
                              ③ قرار المنحة       (سياسة صريحة، فشل مغلق)
                              ④ salla_ingest_event (معاملة واحدة)
                                   ├─ salla_webhook_events  ← تدقيق
                                   ├─ purchase_ledger       ← سجلّ دائم
                                   └─ entitlements          ← المنحة
                                          │
   تسجيل لاحق بنفس البريد ──► claim_pending_grants() ──┘
```

## 2. ما يستهلكه العميل — ثلاث دوال لا رابع

| الدالة | الدور | من ينادي |
|---|---|---|
| `my_entitlement()` | **القراءة الوحيدة المعتمدة.** الحالة تُشتقّ من وقت القاعدة، لا من عمود مخزَّن. | `authenticated` |
| `claim_pending_grants()` | بعد **كل** تسجيل/تأكيد بريد. يلتقط شراءً سبق الحساب. | `authenticated` |
| `redeem_access_code(code)` | استرداد كود وصول. | `authenticated` |

### `my_entitlement()` — الشكل المُعاد

```
state            text   ← الحقل الوحيد الذي تبني عليه الواجهة
entitlement_type text
source           text
activated_at     timestamptz
expires_at       timestamptz
no_expiry        boolean
updated_at       timestamptz
```

**قيم `state` — سبع لا ثامن لها:**

| القيمة | معناها للواجهة |
|---|---|
| `premiumActive` | وصول كامل، بلا انتهاء |
| `specialAccessActive` | وصول بكود، موقوت |
| `trialActive` | تجربة جارية |
| `trialExpired` | التجربة انتهت |
| `revoked` | **محظور** — لا يُرفع بأي مسار خدمة ذاتية |
| `noAccess` | لا منحة |

> ⚠️ **لا تحسب الانتهاء في العميل.** `expires_at` للعرض فقط؛ ساعة الجهاز
> قابلة للتقديم، وساعة القاعدة لا. القرار دائمًا `state`.

> ⚠️ **`revoked` ليست خطأً يُعاد المحاولة عليه.** لا تُخفِها ولا تُترجمها
> «حدث خطأ». نصّها للمستخدم يُحسم في موجة النصوص، لا هنا.

### متى تُنادى `claim_pending_grants()`

**بعد تسجيل الدخول وبعد تأكيد البريد — في الحالتين.** المشتري قد يكون دفع
قبل أن يملك حسابًا أصلًا؛ السجلّ ينتظره في `purchase_ledger`، وهذه الدالة هي
ما يحوّله إلى منحة. تُرجع نفس قيم `state` أعلاه.

وهي **آمنة للتكرار**: نداؤها بلا شراء معلَّق يعيد الحالة القائمة ولا يغيّر شيئًا.

## 3. ما **لا** يفعله العميل — أبدًا

| ممنوع | لماذا |
|---|---|
| كتابة أي صفّ في `entitlements` | لا سياسة كتابة على الجدول أصلًا؛ كل تغيير عبر دالة `SECURITY DEFINER` |
| نداء `admin_grant_premium` أو `salla_ingest_event` | `service_role` حصرًا — يُثبِته `test:salla-webhook` لكل من `anon` و`authenticated` |
| تخزين «هو Premium» محليًا كمصدر حقيقة | كذبة بمجرّد انتهاء المدّة أو الحظر. خزّنه **ذاكرةً مؤقّتة** واقرأ `my_entitlement()` عند كل إقلاع |
| منح وصول من ردّ المتصفّح بعد الدفع | صفحة الشكر ليست إثبات دفع. الإثبات هو الـwebhook وحده |
| توليد كلمة مرور أو إرسالها | ممنوع بالميثاق §0.1. التفعيل يمرّ برابط دعوة أو كلمة مرور يضعها المستخدم |

## 4. متغيّرات البيئة — تُضبط بلوحة Supabase، لا في المستودع

| المتغيّر | إلزامي | ملاحظة |
|---|:--:|---|
| `SUPABASE_URL` · `SUPABASE_SERVICE_ROLE_KEY` | ✅ | تحقنهما المنصّة |
| `SALLA_WEBHOOK_SECRET` | ✅ | استراتيجية التوقيع (الافتراضية لدى سلة) |
| `SALLA_WEBHOOK_TOKEN` | ⬜ | فقط إن استُخدمت استراتيجية الرمز |
| `SALLA_AMOUNT_POLICY` | ✅ | `exact` أو `off` — **الغياب يوقف الطرفية عمدًا** |
| `SALLA_EXPECTED_AMOUNT_MINOR` | ✅ مع `exact` | بأصغر وحدة: `1999` = ١٩٫٩٩ ريالًا |
| `SALLA_EXPECTED_CURRENCY` | ⬜ | افتراض `SAR` |
| `SALLA_PAID_STATUS_SLUGS` | ⬜ | افتراض `completed` وحدها |
| `SALLA_EXPECTED_PRODUCT_IDS` | ⬜ | قائمة بفواصل؛ فارغة = لا فحص منتج |

> **لماذا لا افتراض متساهل لسياسة المبلغ:** أخطر ما تفعله بوابة دفع أن تمنح
> لأن متغيّرًا لم يُضبط. الغياب خطأ تهيئة يوقف الطرفية (`500`)، لا صمتٌ يمنح.

## 5. عقد الردّ — ولماذا الرفض الدائم `200`

سلة **تعيد الإرسال ثلاث مرّات بفواصل ~٥ دقائق** على أي ردّ غير ناجح.

| الحالة | HTTP | السبب |
|---|:--:|---|
| `processed` · `duplicate` · `ignored` · `rejected` | `200` | قرارات **نهائية** — الإعادة لا تغيّرها وتلوّث التدقيق |
| توقيع فاسد/غائب | `401` | طلب لا نعترف به |
| حمولة مشوَّهة | `400` | لا تُصلحها إعادة |
| سوء تهيئة · عطل قاعدة | `500` | **يُراد** أن تُعيد سلة — قد تنجح |

تصنيفات سطر التدقيق: `received` · `verified` · `ignored` · `processed` ·
`duplicate` · `rejected` · `failed`.

**والتمييز بين `ignored` و`rejected` تشغيليّ لا شكليّ:**
`ignored` = ليس لنا أو لم يُدفع بعد. `rejected` = طلب **مدفوع** يخالف السياسة
— يستحق عين إنسان، لا أن يغرق بين آلاف المتجاهَل.

## 6. الثوابت التي يقوم عليها كل ما سبق

1. **`(provider, provider_order_id)` هوية شراء واحدة.** نفس الهوية ⇒ idempotent.
   هوية مختلفة ⇒ `purchase_identity_conflict`، **فشل مغلق**. والمقارنة عبر كل
   إصدارات الملح كي لا يصير دورانه بابًا خلفيًا.
2. **الإلغاء الدائم يعلو على الشراء.** يُسجَّل الشراء (المال حقيقي فأثره يُحفَظ)
   وتُحجب المنحة. `admin_unrevoke` وحده يرفع.
3. **السجلّات الدائمة بلا `user_id`** — تنجو من `delete_own_account()`. وهذا ما
   يجعل «اشتريت» تبقى صحيحة بعد حذف الحساب، و«مرّة واحدة» تعني مرّة واحدة.
4. **لا بريد صريح في أي سجلّ دائم** — بصمة مُملَّحة بإصدار مُرقَّم.
5. **الحالة تُشتقّ ولا تُخزَّن** — لا عمود `status`.

## 7. ما يبقى قبل التفعيل الحقيقي — عوائق مسمّاة

| العائق | بيد من |
|---|---|
| تطبيق الهجرات على staging ثم الإنتاج | **المؤسس** — الميثاق §1 يحجز الهجرة على قاعدة حيّة |
| إنشاء أسرار الإنتاج وتسجيل الـwebhook في لوحة سلة | **المؤسس** |
| **مطابقة `SALLA_PAID_STATUS_SLUGS` بحمولة حقيقية** | يُحسم على staging — التوثيق لا يصرّح أي شريحة تضمن وصول المال |
| تحديد المعدّل (rate limiting) | عائق بنية خارجي معلَن (§11.2 في وثيقة المعمارية) |
| P3–P7: الإعداد · المزوّد · بوّابة المسارات · الشاشة · أدوات الإدارة | موجات لاحقة |
