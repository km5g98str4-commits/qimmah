# P6 Agent 3 — مسح الباركود عبر الكاميرا + Open Food Facts

## الهدف
تسجيل طعام بمسح باركود المنتج بدل البحث اليدوي، مع بحث فوري عبر Open Food Facts (مجاني،
بلا مفتاح، ODbL) ومسار يدوي صادق عند عدم توفّر المنتج.

## الملفات
- `src/features/barcode/openFoodFacts.ts` — استعلام OFF (`GET /api/v2/product/{barcode}.json`)
  + تحويل النتيجة لقيم لكل 100غ + تخزين مؤقت في `localStorage` (`qimmah:off:cache:v1`).
- `src/features/barcode/BarcodeCamera.tsx` — فيديو كاميرا حيّ + مسح مستمر عبر `@zxing/browser`.
- `src/features/barcode/ScanFoodPanel.tsx` — لوحة تُنسّق الحالة: مسح → بحث → نتيجة/فشل/رفض صلاحية.
- تعديلات: `src/components/nutrition/QuickMealLogger.tsx` (زر المسح + الربط مع `selectItem`)،
  `src/i18n/dict/nutritionScreen.ts` (نصوص عربي/إنجليزي)، `src/lib/icons.ts` (Camera, ScanLine)،
  `src/data/foodItems.ts` (فئة جديدة `منتج ممسوح بالباركود`).

## التدفّق
1. المستخدم يفتح لوحة تسجيل الطعام (أي وجبة) → تبويب «ابحث عن طعام» → زر «امسح الباركود 📷».
2. تُفتح لوحة المسح، تطلب صلاحية الكاميرا (لمسة مستخدم قبلها — متوافق مع قيد iOS Safari)
   وتبدأ `BrowserMultiFormatReader.decodeFromVideoDevice`.
3. عند اكتشاف باركود: طلب OFF بحقل `User-Agent: Qimmah/1.0` (يُهمَل من بعض المتصفحات لأنه
   Header محجوز — موثّق أدناه) وحقول `product_name,brands,nutriments,serving_size` فقط.
4. نتيجة ناجحة (بسعرات > 0) → تُبنى كـ `FoodItem` مؤقت (`servingGrams: 100`، القيم = لكل 100غ)
   ويُمرَّر مباشرة لنفس مسار الاختيار من البحث (`selectItem`) — تجربة موحّدة بالغرامات.
5. غير موجود / سعرات ناقصة → «ما لقينا المنتج» + زر «أعد المسح» وزر «إضافة يدوية» يفتح تبويب
   الإضافة اليدوية مباشرة. رفض صلاحية الكاميرا أو متصفح غير مدعوم → نفس مسار الإضافة اليدوية
   برسالة مناسبة. لا يوجد أي طريق مسدود.
6. نسب المصدر: «بيانات المنتج من Open Food Facts (رخصة ODbL)» ظاهرة أسفل لوحة المسح دائمًا.

## قرارات وتوثيق صادق
- **User-Agent**: متصفحات `fetch` تعتبره Header محجوزًا وقد تتجاهله فعليًا — لا يمكن ضمان
  إرساله من جانب العميل. أُبقي في الكود لأنه غير ضار ويوثّق النية، لكنه ليس ضمانًا حقيقيًا
  (هذا قيد منصّة المتصفح لا قصورًا في التنفيذ).
- **تغطية OFF محليًا محدودة**: مُصرَّح بها في نص «ما لقينا المنتج» — لا وعد بتغطية شاملة.
- **حجم الحزمة**: مكتبة `@zxing/browser` (+`@zxing/library`) ثقيلة (~449كِلوبايت / ~114كِلوبايت
  مضغوط). عُزلت عبر `React.lazy` + `Suspense` بحيث لا تُحمَّل إلا عند فتح لوحة المسح فعليًا —
  حزمة `QuickMealLogger` الأساسية بقيت خفيفة (~80كِلوبايت).
- **التخزين المؤقت**: نتائج OFF (موجودة أو غير موجودة) تُخزَّن بالباركود في `localStorage` —
  فشل الشبكة وحده لا يُخزَّن (قد ينجح لاحقًا).

## الإثبات
- استعلام حقيقي عبر `curl` (بدون متصفح) لباركود نوتيلا العالمي `3017624010701`:
  `status:1`، `product_name: Nutella`، `energy-kcal_100g: 539` — يطابق منطق `parseProduct`
  في `openFoodFacts.ts` (يُقرأ من `caloriesPer100g` ويُعامَل كموجود لأن السعرات > 0).
  وباركود غير موجود (`0000000000000`) رجّع `status:0` — يطابق منطق الكود الذي يحوّله لـ
  `null` فيوجّه المستخدم لمسار الإضافة اليدوية.
- `npm run typecheck` ✅ بلا أخطاء.
- `npm run lint` ✅ بلا أخطاء/تحذيرات.
- `npm run build` ✅ — `ScanFoodPanel` (يضم zxing) في حزمة منفصلة محمَّلة عند الطلب فقط
  (448.85كِلوبايت / 113.75كِلوبايت مضغوط)، لا تُحمَّل مع الصفحة الرئيسية.
- تحقّق حي عبر متصفح لم يُنفَّذ في هذه الجلسة: أداة المعاينة في هذه البيئة تُشغّل خادم Vite من
  نسخة العمل الرئيسية المشتركة (`/Users/ziyad/qimmah-deploy`) لا من هذا الـ worktree المعزول
  (`feature/p6-barcode`)، وتلك النسخة الرئيسية بها تعديلات جلسة أخرى غير مُلتزَمة — لذا لم
  يكن ممكنًا تشغيل معاينة حيّة دون التأثير على عمل غير مرتبط. الاعتماد كان على مراجعة الكود
  والبوابات الثلاث أعلاه. **موصى به**: اختبار يدوي على جهاز حقيقي (HTTPS + كاميرا) قبل النشر،
  بباركود عالمي معروف (مثال: `3017624010701` نوتيلا) للتأكد من نجاح الاستعلام، وباركود غير
  موجود للتأكد من مسار الإضافة اليدوية.
