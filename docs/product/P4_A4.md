# P4 · Agent 4 — English language support (full ar/en i18n)

**Branch:** `claude/p4-english-i18n-gzj8g9` (base: P3 release `e6e6f21`)
**Status:** ✅ Complete — gates green, both languages proven to render.
**Why:** Repeated user feedback asked for English. The app was Arabic-only with a
“English coming soon” placeholder in Settings.

---

## 1. i18n approach

Lightweight, **no external dependency** — a React Context over keyed dictionaries.

**Core layer — `src/i18n/`**
- `LanguageContext.tsx` — `LanguageProvider` holds the active language in state, exposes
  `{ lang, dir, t, setLang, toggle }` via `useLanguage()` (+ `useStrings()`, `useLang()` shortcuts).
  On mount and on every change it calls `applyLanguage(lang)` which sets `document.documentElement`
  `lang` + `dir` (ar→`rtl`, en→`ltr`). The choice is persisted to `localStorage` (`qimmah:prefs:v1`)
  through the existing `appPreferences` helpers.
- `LanguageToggle.tsx` — a reusable `عربي/English` control with two variants: `segmented`
  (Settings / full pickers) and `compact` (globe chip for the header / start screen).
- `index.ts` — barrel export.

**Wiring**
- `main.tsx` wraps the tree in `<LanguageProvider>` (outermost app provider).
- `App.tsx` now derives `LANG` from `useLanguage()` instead of the old hardcoded
  `const LANG = 'ar'`. Because every view already received `lang` as a prop, a single context
  state change re-renders **every screen** into the new language — no reload, no route reset.

**Dictionaries — two tiers, one convention**
- **Shell dictionary** (pre-existing, now activated): `src/config/strings.ts` — the typed
  `ShellStrings` interface with full `ar` + `en` (~313 leaf keys). The TypeScript interface
  *guarantees* `en` has every key the app reads, so a missing translation is a compile error, not a
  runtime blank.
- **Feature dictionaries** (new): `src/i18n/dict/*.ts`, one typed `Record<Lang, …>` per screen
  group. These key the copy that was previously **hardcoded Arabic** inside components. Each keeps
  the original Arabic verbatim and adds natural fitness English (not literal translation).

English copy follows a shared glossary (Sets, Reps, Workout, Progressive overload, PRs, Training
volume, Streak, Target, …) so terminology is consistent across screens.

## 3. Language toggle

`عربي / English`, available in three places, all driven by the same context:
- **Settings → Language** (segmented) — replaced the old “coming soon” card. Includes a hint line
  “text and direction switch instantly, saved on this device”.
- **App header** (`MobileShell`, compact globe chip) — quick switch from any main tab.
- **Start screen** (compact chip, top corner) — language choice on first impression.

Behavior: persists to `localStorage`; switches **copy and direction live**; no reload; no route change.

## 4. RTL ↔ LTR proof

Verified headless (Chromium + Playwright) against the production build (`vite preview`):

| Step | `dir` | `lang` | localStorage | Result |
|---|---|---|---|---|
| First load (default) | `rtl` | `ar` | — | Arabic renders ✓ |
| Click toggle → English | `ltr` | `en` | `{"language":"en"}` | “Build my plan now / Log in / Continue as guest” ✓ |
| Reload page | `ltr` | `en` | `{"language":"en"}` | Choice persists ✓ |
| Open `#/demo` (full app) | `ltr` | `en` | — | Today / Nutrition / Progress / Workout / Measurements all English ✓ |

Screenshots captured (start-ar, start-en, demo-en): LTR layout is clean, no overlapping/clipped
text, logical properties (`ms-/me-`, `start-/end-`) mean the existing RTL layout mirrors correctly.
Arabic mode remains pixel-perfect RTL.

No raw key strings ever surface: copy is read from dictionary objects (`t.x` / `d.x`), not a
string-key lookup, and the typed interfaces make an untranslated key a build error.

## 6. Scope decisions & risks

**Bilingual as-is (unchanged, per brief):** exercise names already carry `nameAr`/`nameEn` and render
by language.

**Deliberately left Arabic (data layer, documented limitation):** content that originates in
`src/data/**` or lib helpers with no English variant stays Arabic even in English mode:
- Food / meal / restaurant / ingredient names (brief: don’t machine-translate dish names).
- Supplement, medication, and commitment library item names + categories.
- Muscle-group names & training recommendations, goal/experience-type labels, weekday/day-split
  names, and the daily motivational phrases.

These are **data, not UI chrome** — the toggle switches all interface copy; only user-domain nouns
remain in Arabic. This shows as some Arabic tokens inside otherwise-English cards on data-heavy
screens (nutrition log, wellness lists, muscle map).

**Follow-ups (future):** add `…En` fields (or a lang param) to the data helpers above to reach 100%
English on data-heavy screens. Landing/marketing sections (`Hero`, `Benefits`, `Pricing`, `Faq`, …)
were out of scope — they are not rendered in the current app flow.

**Risk assessment:** Low. Additive change; Arabic default and RTL behavior are unchanged; the typed
dictionaries prevent missing-key regressions; no new runtime dependency was added.
