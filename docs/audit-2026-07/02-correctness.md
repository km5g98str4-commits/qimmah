# تدقيق قِمّة — الصحّة الحسابية والحالات الحديّة (2026-07-25)

**النطاق:** `src/lib/*` (الحسابات، التواريخ، السلاسل، التغطية، المولّد، التحقّق) + مسارات الإدخال في `src/components` و`src/views`.
**الطريقة:** قراءة الكود سطرًا بسطر + تشغيل فعلي للمولّد والحاسبات عبر حزم `esbuild` معزولة (لم يُعدَّل أي ملف كود). كل رقم في هذا التقرير ناتج تشغيل حقيقي، لا تقدير.

---

## ملخّص تنفيذي (٥ أسطر)

1. **«تمرين اليوم» لا يطابق الجدول الذي ولّده التطبيق نفسه**: `todayPlanDay` يختار اليوم بـ `new Date().getDay() % days.length`، فيعرض تمرينًا في أيام الراحة ويعرض يومًا مختلفًا عن الجدول المكتوب في الشاشة نفسها (تحقّق فعلي: جدول ٤ أيام يعرض «اليوم ٣» يوم السبت بينما الجدول يقول «اليوم ١»).
2. **الحساسيات الغذائية ونمط الأكل يُجمعان في الإعداد ولا يُقرآن أبدًا**: مستخدم يختار «لاكتوز + مكسّرات + بيض + مأكولات بحرية» يستلم خطة كل وجباتها تحتوي مسبّبًا معلنًا (بيض، سلمون، زبادي ومكسّرات، واي وحليب).
3. **انفصام في تخزين القياسات**: الواجهة تقرأ المفتاح القديم بينما الاستيراد والمزامنة يكتبان في المتجر الجديد → القياسات المستعادة لا تظهر، وحذف قياس واحد **يمسح** كامل قياسات المتجر التاريخي.
4. **الحسابات تُنتج تناقضات صامتة**: الماكروز قد تتجاوز السعرات المستهدفة بـ ١٨٪ (الكارب يُقصّ لصفر)، وجلسات ٣٠ دقيقة تولّد أسبوعًا كاملًا بلا أي تمرين ذراع أو كور، وبطاقات التغطية تصف خطة التطبيق نفسها بأنها «إفراط تدريبي».
5. لا شيء من هذا ينهار بصريًا — كلّه أرقام خاطئة تبدو صحيحة، وهذا أخطر ما في التقرير على منتج يُباع بوعد «الدقّة».

### C-01 · «تمرين اليوم» يتجاهل الجدول الأسبوعي وأيام الراحة

**الملف:** `src/lib/workoutPlan.ts:65-69` (المستهلكون: `src/views/WorkoutView.tsx:33`, `src/views/DashboardView.tsx:38,231,267`, `src/sections/Today.tsx:45`)
**الخطورة:** critical · **التصنيف:** date-logic

**الدليل:**
```ts
/** يختار يوم اليوم من الخطة حسب يوم الأسبوع (تدوير على عدد الأيام). */
export function todayPlanDay(plan: WorkoutPlan): PlanDay | undefined {
  if (!plan.days.length) return undefined
  const index = new Date().getDay() % plan.days.length
  return plan.days[index]
}
```
الجدول الحقيقي يُبنى في مكان آخر تمامًا (`planGenerator.ts:674-690`) ويُحفظ في `customization.routine`، ويبدأ من **السبت** ويحتوي أيام راحة. أمّا `getDay()` فيبدأ من **الأحد** ولا يعرف الراحة.

تشغيل فعلي (خطة ٤ أيام، علوي/سفلي):
```
الجدول المولّد : السبت=اليوم ١ · علوي | الأحد=اليوم ٢ · سفلي | الإثنين=راحة | الثلاثاء=اليوم ٣ · علوي | الأربعاء=اليوم ٤ · سفلي | الخميس=راحة | الجمعة=راحة
todayPlanDay   : السبت→اليوم ٣ | الأحد→اليوم ١ | الإثنين→اليوم ٢ | الثلاثاء→اليوم ٣ | الأربعاء→اليوم ٤ | الخميس→اليوم ١ | الجمعة→اليوم ٢
```

**الأثر:** ٧ أيام من ٧ تعرض «ابدأ تمرين اليوم» — بما فيها الأيام الثلاثة التي كتب فيها التطبيق «راحة واستشفاء». ويوم السبت تعرض الرئيسية «اليوم ٣ · علوي» بينما جدول الأسبوع في الشاشة نفسها يقول «اليوم ١ · علوي». المستخدم الملتزم يتمرّن ٧ أيام ظنًّا أنه يتبع الخطة، ويكرّر «علوي» مرّتين متتاليتين.

**الإصلاح:** اجعل `todayPlanDay` تقرأ `customization.routine` (مصدر الحقيقة الوحيد للجدولة): طابق يوم الأسبوع الحالي على فهرس `WEEKDAYS` (السبت=0) عبر `(new Date().getDay() + 1) % 7`، وأعِد `undefined` إن كان النوع `rest`، وإلا أعِد يوم الخطة المقابل لترتيب أيام التمرين. مرّر `routine` كوسيط للدالة بدل قراءة الخطة فقط، ثم أضف حالة «اليوم راحة» في الواجهات الثلاث.
**الجهد:** M

### C-04 · الماكروز تتجاوز السعرات المستهدفة (الكارب يُقصّ لصفر بلا تنبيه)

**الملف:** `src/lib/calculators.ts:220-224`

**الدليل:**

البروتين والدهون يتناسبان مع الوزن (16.1 سعرة/كجم مجتمعين) بينما السعرات المستهدفة تتناسب مع BMR/النشاط، فينكسر الاتزان عند الأوزان العالية مع نشاط منخفض. تشغيل فعلي (`computeTargets`) لأنثى ١٤٠ كجم/١٥٠ سم/٦٠ سنة، خامل، يوم تمرين واحد، تنشيف:

```json
{"targetCalories":1899,"proteinGrams":280,"fatGrams":126,"carbsGrams":0,
 "مجموع سعرات الماكروز":2254,"الفرق":"+355 سعرة (+18.7%)","notes":""}
```

**الأثر:** التطبيق يعرض «هدفك ١٨٩٩ سعرة» وتحته ماكروز مجموعها ٢٢٥٤ سعرة، وكارب = صفر غرام بلا أي شرح. المستخدم الذي يلتزم بالماكروز يفشل هدف السعرات حتميًا؛ والذي يلتزم بالسعرات يفشل البروتين. لا `notes` ولا تحذير يظهر (عتبة التنبيه لا تلتقط الحالة لأن الخام ١٨٩٩ > BMR).

**الإصلاح:** بعد حساب الكارب، تحقّق `protein*4 + fat*9 > calories`: خفّض الدهون أولًا حتى 0.6غ/كجم، ثم البروتين حتى 1.6غ/كجم، ثم — إن بقي التجاوز — ارفع `targetCalories` لأرضية `protein*4 + fat*9 + 50` وأضف ملاحظة عربية صريحة. وبديهيًا: اسقف البروتين على الوزن المستهدف لا الحالي عند BMI مرتفع. أضِف اختبارًا يثبّت الثابتة: `|Σ الماكروز − targetCalories| ≤ 20 سعرة` لكل مدخل ضمن حدود `LIMITS`.

### C-21 · مؤقّت الراحة يتأخّر عن الزمن الحقيقي عند تصغير التطبيق

**الملف:** `src/components/WorkoutMode.tsx:109-117`
**الخطورة:** low · **التصنيف:** race/timing

**الدليل:**
```ts
useEffect(() => {
  if (!timer.running) return
  if (timer.left <= 0) { setTimer((p) => ({ ...p, running: false })); return }
  const id = window.setTimeout(() => setTimer((p) => ({ ...p, left: p.left - 1 })), 1000)
  return () => window.clearTimeout(id)
}, [timer.running, timer.left])
```
عدّاد تنازلي مبني على سلسلة `setTimeout` بلا مرجع زمني مطلق.

**الأثر:** المتصفح/WKWebView يخنق المؤقّتات في الخلفية. من يخفض الهاتف ٩٠ ثانية بين المجموعات يعود ليجد «باقي ٤٠ ثانية» على راحة مدّتها ١٢٠ — فيرتاح ~٣ دقائق فعليًا. مقياس تدريبي أساسي (زمن الراحة) يصبح غير موثوق تحديدًا في الاستخدام الطبيعي.

**الإصلاح:** خزّن `endsAt = Date.now() + sec*1000` واحسب `left = Math.max(0, Math.ceil((endsAt - Date.now())/1000))` داخل `setInterval(…, 250)`، وأعِد الحساب عند `visibilitychange`.
**الجهد:** S
