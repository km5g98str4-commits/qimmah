## القرارات الثلاثة التي تستحق الشرح

### ١) ختم `updated_at` ثانٍ — وليس تكرارًا

`set_updated_at()` المشترك يكتب `now()` في كل UPDATE. هذا صحيح حين يكون
`updated_at` مجرّد دفتر حسابات، وخطأ هنا: العميل **يقرأ** `row.updated_at` كدليل
حسم LWW (`hydrateCoverageFromCloud` لـ`nutrition_ledger`، وhydrate الأقدم
لـ`measurement_logs` الذي يكتبه أيضًا في السجل المحلي). ختم `now()` يجعل كل صف
سحابي أحدث من التعديل الذي يمثّله → جهاز يحمل تعديلًا محليًا **أحدث فعلًا** قد
يخسر المقارنة ويُدهس. وهذا بالضبط ما تَعِد الوثيقة بألّا يحدث («لا حذف صامت»).

`set_updated_at_lww()`: إن أرسل الكاتب طابعًا جديدًا نُبقيه حرفيًا (هو الدليل)،
وإلّا نختم `now()` (فلا يبقى فارغًا ولا قديمًا). المخاطرة المعاكسة محسوبة: إبقاء
طابع قديم قد يُتيح لجهاز آخر أن يدهس الصف (**قابل للاسترجاع** — البيانات موجودة
على الجهازين)، بينما ختم `now()` قد يحذف تعديلًا أحدث (**غير قابل للاسترجاع**).

### ٢) لا فهارس إضافية — عمدًا

كل مفتاح فريد أعلاه هو فهرس btree عموده الأول `user_id`، وهو **مسار الوصول
الوحيد** الذي يستعمله العميل (`select * … eq('user_id', uid)`) وما يحتاجه
`ON DELETE CASCADE`. إضافة `(user_id, date desc)` — كما في الهجرات 0002/0003 —
تكرار محض: Postgres يمسح الـbtree للخلف فيخدم الترتيب التنازلي من الفهرس
الصاعد نفسه. الفهرس غير المستعمَل ليس مجانيًا (تضخيم كتابة في كل دفعة مزامنة)،
فتُرك عمدًا لا سهوًا.

### ٣) قيد الخصوصية على شواهد القبر

`deleted_at is null or data = '{}'::jsonb` (ولـ`measurement_logs`:
`values = '{}' and notes is null`). `tombstoneRow()` يمسح الحمولة أصلًا؛ القيد
يجعل «المحذوف يبقى مقروءًا سحابيًّا» **غير قابل للتمثيل** لا مجرّد غير محتمَل.

## البرهان

```bash
npm run test:db-schema   # دون شبكة — ضمن test:gate
npm run db:verify        # على مشروع Supabase حيّ (staging)
```

**`test:db-schema` (٣٥٩ فحصًا)** يقرأ `SyncTable` من العميل ومجلد الهجرات ويثبت:
عقد الأعمدة والمفاتيح لكل جدول؛ RLS + أربع سياسات مالك-فقط؛ **عزل حسابين**
بتنفيذ المُسنِدات المستخرَجة من نص الهجرة نفسه على مجموعة صفوف لحسابين (تعبير لا
يتطابق مع الصيغة القانونية = **فشل**، لأن «غير معروف» ليس «آمن»)؛ أعمدة شواهد
القبر؛ قابلية إعادة التشغيل وعدم التدمير؛ وتطابق `SUPABASE-SCHEMA.sql` المحلي.

**`db:verify`** هو البرهان التجريبي على قاعدة حقيقية بحسابين مؤقتين: كتابة
المالك تنجح، وselect **بلا فلترة** يرجع صفوف المالك فقط، والقراءة/التعديل/الحذف
عبر الحسابات صفر، وanon صفر، وشاهد القبر يُقبل ممسوحًا ويُرفض حاملًا حمولة،
والطابع لا يُدهس، ثم `delete_own_account` يمسح كل شيء.

البرهان الساكن **لا يغني** عن الحيّ: هو لا يثبت أن Postgres يقبل هذا الـSQL.

## قبل تفعيل المزامنة (بوابة المالك)

1. `supabase db push` على **staging** أولًا (أو لصق الملفات بترتيب الاسم).
2. `npm run db:verify` بمفاتيح staging — يجب أن تخرج كلها خضراء.
3. لوحة Supabase → Database → Advisors: بلا فجوات RLS.
4. عندها فقط يُدرس `VITE_SYNC_ENABLED=true` لاختبار جهاز — قرار مالك منفصل.
