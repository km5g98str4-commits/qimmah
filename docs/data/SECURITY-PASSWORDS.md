# العقد الأمني — كلمات المرور ودعم الطوارئ (وثيقة عقد، لا تنفيذ)

**المبدأ:** كلمات المرور ملك المستخدم وحده. Supabase Auth يخزّنها **hashed (bcrypt)** على الخادم؛ لا يمر نصّها الصريح بأي طبقة نملكها بعد لحظة الإرسال لـ`signInWithPassword`/`signUp` عبر HTTPS.

## المحظورات المطلقة (مُتحقَّق منها آليًا في `test:data-safety`)
1. **لا تخزين** لكلمة مرور كنص صريح — لا في localStorage ولا ملفات ولا حالة دائمة. *(grep: `localStorage.setItem(...password` = 0)*
2. **لا إظهار** لكلمة مرور لأي طرف — مالكًا كان أو أدمن. لا يوجد ولن يوجد مسار «عرض كلمة مرور مستخدم».
3. **لا تسجيل** لكلمات المرور في logs/monitoring — *(grep: `console.*password` = 0؛ وSentry مقيَّد بميتاداتا — راجع سياسة monitoring.ts)*.
4. **لا `service_role`** في كود العميل أو env بادئة `VITE_*` — مفتاح الخدمة يعيش في بيئة خادم/لوحة Supabase فقط. *(grep: `service_role` في src = 0؛ وقاعدة `.claude/rules/security.md` القائمة: كل `VITE_*` عام)*.
5. **لا backdoor ولا impersonation** غير مدقَّق — أي دخول باسم مستخدم بغير جلسته محظور بنيويًا في العميل.

## دعم الطوارئ (لاحقًا — عبر أدوات Supabase الإدارية، ليس عبر التطبيق)
| الحاجة | الأداة المشروعة |
|---|---|
| مستخدم فقد الوصول | **إرسال إعادة تعيين كلمة المرور** (بريد rest link — موجود أصلًا في التطبيق) |
| جلسة مسروقة/مريبة | **إنهاء الجلسات** (Admin API: sign out user / revoke refresh tokens) |
| حساب مسيء | **تعطيل/حظر الحساب** (ban_duration في Admin API) |
| بريد مفقود/خاطئ | **تغيير البريد بإجراء إداري مدقَّق** (Admin API + توثيق السبب) |
| المحاسبة | **Audit Log**: كل إجراء إداري يُسجَّل (من، متى، ماذا، لماذا) — شرط مسبق لأي لوحة إدارة |

**قاعدة اللوحة الإدارية المستقبلية:** تُبنى على Admin API بمفتاح خادم خارج العميل، خلف مصادقة منفصلة + سجل تدقيق، ولا تكشف أبدًا هاش كلمة المرور فضلًا عن نصّها. **لا لوحة في هذه الموجة.**
