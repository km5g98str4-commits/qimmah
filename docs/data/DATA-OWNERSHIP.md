# ملكية البيانات المحلية — الجرد والخطة (موجة سلامة البيانات v1)

**الأساس:** cc96d84 · الفرع: `claude/foundation-data-safety-v1` · **مصدر الحقيقة البرمجي:** `src/lib/userDataKeys.ts` (هذا الملف عرضٌ له — عند التعارض، السجل البرمجي هو الحاكم).

## القاعدة
- **بيانات مستخدم** (صحة/تدريب/تغذية/تقدّم/تفضيلات حساب) ⇒ يجب أن تكون منسوبة لـuser ID.
- **إعداد جهاز** (لغة/ثيم/كاش مجهول/أعلام واجهة) ⇒ يبقى عامًا ولا يُنسخ لكل مستخدم.
- النسبة اليوم تتم بطبقتين: **ختم الملكية** `qimmah:dataOwner:v1` + عزل التبديل (wipe) + **بوابة التبنّي** (بيانات مجهولة المالك لا تُرفع). التوسيم البنيوي `<key>:u:<uid>` هو خطة الموجة التالية (عمود «الهجرة»).

## ما نفّذته هذه الموجة (سلوك، لا نقل مفاتيح)
1. **LWW فعلي** (`syncLww.ts` + `mergeCloudIntoSnapshot`): حسم لكل سجل بطابع `updated_at`/`updatedAt`؛ الكيانات المعلّقة بطابور الرفع محمية؛ لا حذف صامت (المحلي غير الموجود سحابيًا يبقى دائمًا)؛ `daily_logs` تُحسم لكل شريحة على حدة. القياسات صارت تحمل `updatedAt` (القديم يسقط لدقّة اليوم).
2. **ختم الملكية** (`dataOwnership.ts`): `qimmah:dataOwner:v1` يسجّل مالك مجموعة البيانات العالمية؛ يُختم عند التبديل الحقيقي (بعد المسح) وعند الدخول على جهاز نظيف.
3. **بوابة التبنّي:** دخول حساب حقيقي فوق بيانات بلا ختم/بختم ضيف ⇒ «تبنٍّ معلّق» — البيانات تبقى محلية وتُقرأ، و`syncAllowedFor` **يحجب الرفع** حتى قرار صريح: `adoptPendingData(uid)` أو `discardPendingData()` (واجهة القرار شأن طبقة UI — الدوال جاهزة وموثقة).
4. **مشغّل هجرات موحّد:** versioned + idempotent + snapshot قبل الكتابة + verify بعد النقل + rollback كامل عند الفشل + **لا حذف للمصدر إلا بعد نجاح مثبت** (`runMigration`).
5. **الحجر:** `quarantineUnscopedUserData` يعزل البيانات غير القابلة للنسبة تحت `qimmah:quarantine:v1:*` — لا تُقرأ ولا تُرفع ولا تُحذف.

## خطة الموجة التالية (نقل المفاتيح — موثَّقة لا منفَّذة)
لكل مفتاح `owner-suffix`: هجرة عبر `runMigration` تنسخ `<key>` → `<key>:u:<dataOwner>` وتتحقق ثم تحذف الأصل؛ تحديث نقطة القراءة/الكتابة في الوحدة المالكة + **تحديث استراتيجية المفتاح في `portability/registry.ts` بنفس الـPR** (العقد المشترك مع الاستيراد/التصدير — سبب تأجيله عن هذه الموجة)؛ ثم تحويل `wipeUserData` لمسح legacy فقط. الترتيب الآمن: historyStore ×8 → خطوات ×3 → البقية. `retire`: حذف توائم legacy + `activeSession` الميت بعدها.

## المخاطر المتبقية (بصراحة)
- التوسيم البنيوي لم يُنفَّذ بعد — العزل الحالي = ختم + بوابة تبنٍّ + مسح تبديل (ثلاث طبقات بدل واحدة، لكن ليس عزل مفاتيح).
- المخازن المساعدة (خطوات/إنجازات/خطة/todo) بلا طوابع لكل سجل — حمايتها LWW عبر الطابور فقط؛ إضافة `updated_at` لصفوفها ترشيح للموجة التالية.
- قرار التبنّي يحتاج واجهة (Codex) — حتى حينها: sync محجوب للحالة المعلّقة (fail-safe).
